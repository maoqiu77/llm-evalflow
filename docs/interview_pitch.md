# LLM EvalFlow 项目面试讲解稿

## 一、30 秒介绍版

这是一个我从 AI 产品经理视角设计的大模型问答评测平台，名字叫 LLM EvalFlow。它解决的不是“怎么调用模型”，而是“怎么更合理地比较多个模型回答的质量”。

我把评测流程做成了一个闭环：先配置评测集，再让多个模型回答同一问题，然后通过硬规则和独立评审模型做六维评分，自动识别 Badcase，最后沉淀优化建议和 Prompt 迭代记录。这个项目的重点是让评测结果更统一、可解释、可复盘，而不是只做一个模型 demo。

## 二、1 分钟介绍版

这个项目叫 LLM EvalFlow，是一个面向 AI 产品经理、问答策略和 Agent 产品岗位的轻量评测平台。

我做它的背景是，很多 AI 产品评测还停留在 Excel 里人工记录问题、收集模型回答、手工打分、再复盘 Badcase，流程很分散，也很难统一口径。所以我希望把这个过程做成一个本地优先的 Web 平台。

它的核心流程是：

1. 先维护评测集，包括问题、场景、难度和期望行为；
2. 然后选择多个模型生成回答；
3. 再通过“硬规则 + 独立评审模型”做六维评分；
4. 对低分回答自动归因为 Badcase；
5. 最后把问题沉淀到 Prompt 迭代和评测报告里。

我觉得这个项目最重要的点不是技术栈本身，而是我在里面重点设计了评测逻辑和公平性，比如不用唯一标准答案，而是用“期望行为”作为评分口径，并且避免让模型给自己打分。

## 三、2 分钟项目讲解版

这个项目叫 LLM EvalFlow，定位是一个大模型问答评测与 Badcase 归因分析平台。

我做这个项目的出发点，是因为 AI 产品经理在做模型效果验收、竞品分析或者 Prompt 迭代的时候，最痛的点通常不是“调模型 API”，而是评测流程很散：问题在 Excel 里、回答在不同页面里、评分标准不统一，Badcase 也很难系统沉淀。

所以我把整个流程做成了一个轻量化平台。

在产品流程上，它分成几块：

- 第一块是评测集管理，可以新增问题、导入 CSV、标注场景和难度；
- 第二块是模型对比，对同一问题批量生成多个模型回答；
- 第三块是自动评分，评分不是简单给总分，而是按准确性、完整性、指令遵循、可执行性、格式稳定性、用户体验六个维度打分；
- 第四块是 Badcase 归因，把低分样本标记成事实错误、信息遗漏、格式不稳定、安全边界不足等类型；
- 第五块是 Prompt 迭代和评测报告，用来支持后续优化闭环。

技术上我用了 FastAPI + React + SQLite，但我认为项目最大的亮点不是技术栈，而是评测方法设计。

因为开放式问答没有唯一标准答案，所以我没有把参考答案设计成唯一文本，而是定义成“期望行为 / 评分参考口径”。也就是说，系统关心的是模型有没有覆盖关键步骤、有没有越过能力边界、有没有编造实时结果，而不是它是否复述某一段固定答案。

在评分公平性上，我做了两层机制：

- 第一层是硬规则，先处理空回答、调用失败、伪工具调用、实时数据编造等明显错误；
- 第二层才是独立评审模型做六维评分。

另外，如果被评模型和评审模型相同，系统会自动切换备用评审模型，降低自评偏差。

所以这个项目本质上不是一个“多模型展示 demo”，而是一个帮助产品经理更系统地做模型评测、发现 Badcase、推动 Prompt 与策略迭代的工作流工具。

## 五、面试官高频追问回答模板

### 1. 你这个项目的“标准答案”是怎么定义的？
我后来刻意不用“标准答案”这个说法，而是叫“期望行为”或“评分参考口径”。因为开放式问答没有唯一正确文本，我真正关心的是模型是否覆盖关键步骤、是否遵守工具边界、是否避免高风险错误。所以它本质上更像一个产品验收标准，而不是文本匹配答案。

### 2. 为什么这些期望行为可以作为评分标准？
因为它们不是随意写的，而是根据真实产品场景手工设计出来的，重点看任务完成度、业务流程正确性、安全边界和用户体验。比如工具调用类问题，重点不是说得多自然，而是有没有识别到需要实时工具、没有工具时会不会编造结果。

### 3. 评分是谁来做的？
评分是两层机制。第一层是硬规则，处理空回答、调用失败、伪工具调用、编造实时数据等明显错误；第二层是独立评审模型，对照用户问题、期望行为和模型回答，从六个维度打分。这样可以兼顾稳定性和灵活性。

### 4. 这样评分公平吗？
我不会说它绝对公平，但它比纯人工主观打分更统一、也更可复盘。因为所有模型面对同一批 Case，使用同一套评分口径；同时先用硬规则处理明显错误，再用独立评审模型细分评分。如果被评模型和评审模型相同，还会自动切换备用评审模型，降低自评偏差。

### 5. 这个系统有哪些局限？
当前的局限主要有三类：第一，期望行为还是人工编写，存在主观性；第二，默认主要依赖单一评审模型，仍可能有偏差；第三，还没有完整接入人工复核、多评审模型投票和黄金样本校准。也正因为我意识到这些局限，所以我在项目里把它们写成了后续优化方向。

### 6. 如果继续迭代，你会先优化什么？
我会优先做三件事：
1. 把期望行为从一段文本升级成结构化评分点；
2. 给高风险和高分歧样本增加人工复核；
3. 对工具调用、安全合规等场景引入差异化评分权重。

这样项目会从“自动评分工具”进一步升级成更适合真实 AI 产品团队使用的评测系统。

## 六、模拟面试问答（建议重点准备）

### 1. 你为什么会想到做这个项目？
我做这个项目的出发点，不是单纯想做一个大模型调用 demo，而是因为我发现 AI 产品经理在做模型效果验收、竞品分析和策略迭代时，最耗时间的其实是重复性的评测工作：整理问题、收集回答、统一标准、复盘 Badcase。很多时候这些信息散落在 Excel、文档和不同网页里，不仅低效，而且很难统一口径。所以我想做一个轻量评测平台，把这些流程结构化。

### 2. 这个项目解决了什么核心问题？
它解决的核心问题是：如何更系统地比较多个模型回答质量，并把评测结果真正用于产品迭代。也就是说，它不仅回答“哪个模型分数高”，还希望回答“为什么低分、问题属于什么类型、下一步怎么优化”。

### 3. 你为什么不用唯一标准答案，而改成期望行为？
因为开放式问答很多时候没有唯一正确文本答案。如果强行用唯一答案去比，容易误伤那些表达不同但本质正确的回答。所以我把参考答案设计成“期望行为 / 评分参考口径”，本质上是一个简化的 Rubric。这样评测关注的是关键步骤、边界意识和任务完成度，而不是文本表面相似度。

### 4. 你怎么保证这个项目的评分相对公平？
我主要从四个方面控制：
1. 同一批 Case 对所有模型统一评测；
2. 所有回答对照同一套期望行为口径；
3. 先用硬规则处理明显错误，避免语言包装掩盖本质问题；
4. 正常回答再交给独立评审模型打分，如果被评模型和评审模型相同，自动切换备用评审模型，降低自评偏差。

所以我不会说它绝对公平，但它比纯人工主观打分更统一、也更可复盘。

### 5. 你说“硬规则 + 独立评审模型”，为什么要这样分两层？
因为如果完全交给评审模型，有些明显错误会被“语言流畅”掩盖，比如空回答、调用失败、伪工具调用、实时结果编造。硬规则适合处理确定性问题，稳定、可解释；独立评审模型适合处理开放式质量判断，比如完整性、用户体验、表达结构。两层结合后，评分既更稳，也更接近真实产品验收逻辑。

### 6. 如果面试官说：评审模型本身也会有偏差，你怎么回答？
我会直接承认这一点。这个项目并不假装自动评分是绝对客观的。当前版本更像是一个“统一口径的自动初筛系统”，它的目标是提高评测效率和一致性，而不是彻底替代人工判断。也正因为如此，我在后续优化里明确规划了人工复核、多评审模型投票和黄金样本校准。

### 7. 这个项目最难的部分是什么？
我觉得最难的不是前后端实现，而是评测方法设计。具体包括三点：
- 期望行为怎么定义，既不能太空也不能太死；
- 不同场景下，什么叫“好回答”，标准并不完全一样；
- 如何避免评分看起来很精确，但其实不可解释。

所以我后面重点加强的是公平性说明、评分逻辑和文档，而不是盲目加更多功能。

### 8. 这个项目和普通“模型聚合展示页”有什么区别？
普通模型展示页更多是把多个模型回答摆在一起给人看，而我这个项目更强调评测闭环：
- 有评测集和场景设计
- 有评分维度
- 有 Badcase 分类
- 有优化建议
- 有 Prompt 迭代与报告沉淀

也就是说，它不只是“看结果”，而是帮助产品经理形成“发现问题—归因问题—推动优化”的工作流。

### 9. 你在这个项目里体现了哪些产品经理能力？
我觉得主要体现了四类能力：
1. **问题抽象能力**：把零散评测流程抽象成标准化闭环；
2. **评测体系设计能力**：定义场景、维度、Badcase 类型和方法口径；
3. **结果复盘能力**：不仅出分，还沉淀归因与优化建议；
4. **产品落地能力**：把方法论真正做成一个可运行、可展示、可迭代的工具。

### 10. 如果你继续做下去，最优先会优化什么？
我会优先做三件事：
1. 把期望行为从文本升级为结构化评分点；
2. 给高风险和高分歧样本增加人工复核；
3. 对工具调用、安全合规等场景引入差异化评分权重。

这样项目会从一个轻量评测平台，进一步升级成更贴近真实 AI 产品团队使用方式的评测系统。

### 11. 你怎么看待“竞品对比”在这个项目里的价值？
我认为竞品对比的价值不只是看谁平均分更高，而是看不同产品在不同场景下的能力边界。比如有的模型更擅长结构化回答，有的更擅长长尾理解，有的在工具边界和安全提醒上更稳定。对于产品经理来说，这种差异比单一总分更有价值，因为它能直接影响产品选型、路由策略和 Prompt 策略。

### 12. 如果面试官问：这个项目更像产品项目还是技术项目？
我会说它本质上是产品项目，技术实现只是承载方式。因为我最想展示的不是我会不会搭 FastAPI 和 React，而是我对 AI 产品评测这件事本身有没有形成方法论：怎么定义口径、怎么尽量保证公平、怎么让结果支持后续策略优化。这部分才是我觉得最能体现产品经理能力的地方。
