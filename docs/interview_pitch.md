## 30 秒介绍版

LLM EvalFlow 是我从 AI 产品经理视角设计的大模型问答评测平台。

它解决的问题不是“怎么调用多个模型”，而是“怎么用统一口径比较模型回答质量，并把 Badcase 变成可复盘、可展示、可迭代的产品资产”。

我把流程做成了一个闭环：维护评测集，生成或导入多模型回答，通过硬规则和独立评审模型做六维评分，自动识别 Badcase，最后输出 Gemini 总览总结、Markdown 报告和 GitHub 静态展示。这个项目的重点是 AI 产品评测方法论和产品化落地，而不是单纯的技术 demo。

## 1 分钟介绍版

这个项目叫 LLM EvalFlow，是一个面向 AI 产品经理、问答策略和 Agent 产品岗位的轻量评测平台。

我做它的背景是：在做模型效果验收、竞品分析或 Prompt 迭代时，很多评测流程还停留在 Excel 和手工复制阶段。问题、模型回答、评分、Badcase 原因和报告分散在不同地方，导致评分口径不统一，复盘成本高，也不方便向面试官、团队或 GitHub 展示结果。

所以我把它做成了一个本地优先的 Web 平台，核心流程包括：

1. 维护评测集，支持新增、编辑、删除、CSV 导入、搜索和场景筛选；
2. 对同一问题生成或复用多个模型回答，支持回答存档，避免重复消耗 API；
3. 用“硬规则 + 独立评审模型”做六维评分；
4. 自动识别低分回答并做 Badcase 归因；
5. 用 Gemini 生成总览总结，并导出 Markdown 报告、README 截图和 GitHub Pages 静态快照。

这里我比较重视的一点是，开放式问答没有唯一标准答案，所以我没有做文本匹配，而是把 `expected_answer` 定义成“期望行为 / 评分参考口径”。这样评测关注的是任务完成度、边界意识和用户体验，而不是模型有没有复述某一段固定答案。

## 2 分钟项目讲解版

LLM EvalFlow 的定位是一个大模型问答评测与 Badcase 归因分析平台。

我做这个项目的出发点，是 AI 产品经理在模型选型、效果验收和 Prompt 迭代时，经常会遇到三个问题：

1. **评测流程分散**：问题在 Excel 里，回答在不同模型页面里，评分标准靠人工理解。
2. **结果难复盘**：只知道哪个模型分数低，但不知道低在哪里、属于什么类型、下一步怎么优化。
3. **展示成本高**：本地跑完评测后，结果不容易沉淀成可对外展示的报告或静态页面。

所以我把这个流程产品化成几个模块：

1. **评测集管理**：支持新增 Case、编辑、删除、CSV 导入、搜索、场景筛选，并展示回答覆盖和评分进度。
2. **模型对比**：对同一问题生成或导入多个模型回答，支持一键生成全部模型回答、只回答新增问题，以及单条补评分。
3. **六维评分**：从准确性、完整性、指令遵循、可执行性、格式稳定性、用户体验六个维度评分。
4. **Badcase 归因**：把低分样本归类为事实错误、答非所问、信息遗漏、格式不稳定、安全边界不足等类型，并保留评分原因和优化建议。
5. **总结和展示**：用 Gemini 生成评测总览，导出 Markdown 报告、`demo-data.json` 静态快照和 README 关键页面截图，让 GitHub Pages 在没有后端的情况下也能展示结果。

我认为这个项目最核心的不是技术栈，而是评测方法和产品闭环设计。

第一，开放式问答没有唯一标准答案，所以我把参考答案改成“期望行为”。比如用户问“查天气并提醒我带伞”，评测重点不是模型说法是否和参考文本一致，而是它有没有识别到天气查询和提醒创建都需要工具能力；没有工具时，是否明确说明限制，而不是编造实时天气。

第二，评分不是完全交给大模型主观判断，而是分成两层。第一层先用硬规则处理空回答、调用失败、伪工具调用、实时信息编造等明显问题；第二层再交给独立评审模型做六维评分。这样可以避免语言很流畅的错误回答拿到不合理高分。

第三，我做了数据复用和展示闭环。模型回答会进入本地回答存档，新增问题可以只生成缺失回答；导出 GitHub 展示时，会生成静态数据、报告和截图。这样它不只是本地 demo，而是能沉淀成可展示、可复盘的项目资产。

所以这个项目本质上不是一个多模型展示页，而是一个帮助产品经理完成“设计评测 - 发现问题 - 归因问题 - 输出建议 - 展示结果 - 推动迭代”的轻量工作流工具。

## 项目更新后值得主动讲的新增亮点

1. **评测集从静态录入升级为可运营对象**
   支持新增、编辑、删除、搜索、筛选和进度查看。面试时可以说：这让 Case 不只是一次性样本，而是可以持续维护的评测资产。

2. **批量流程更接近真实评测效率需求**
   支持一键生成全部模型回答、一键自动评分、单条补评分，以及只回答新增问题。面试时可以说：这是为了降低每次回归评测的重复操作成本。

3. **回答存档降低重复调用成本**
   模型回答会保存到本地存档，命中后可复用历史回答，不必每次都重新调用 API。面试时可以说：这是在平衡演示稳定性、成本和评测可复现性。

4. **GitHub 静态展示解决项目可见性**
   本地动态模式用于评测，GitHub 静态模式用于展示。导出后生成 `demo-data.json`、报告和截图，GitHub Pages 不需要运行 FastAPI 也能展示结果。

5. **Gemini 总览总结让结果更像产品报告**
   总览页可以调用 Gemini 汇总模型表现、场景差异、Badcase 归因和优化建议。面试时可以说：这一步把评分数据转成产品经理能汇报的结论。

## 面试时推荐演示顺序

如果面试官让你现场介绍项目，建议按这个顺序演示，不要一开始就讲代码。

1. **先看 Dashboard**
   说明它能看到题库规模、完成进度、模型平均分、Badcase 分布和 Gemini 总览总结。

2. **进入评测集**
   讲 Case 不是只有问题文本，还包括场景、难度和期望行为；同时展示新增、编辑、删除、搜索和筛选，说明评测集可以持续运营。

3. **进入模型对比**
   展示同一问题下不同模型回答的差异，强调“一键生成全部模型回答”和“回答新增问题”降低回归评测成本。

4. **展开评分依据**
   重点讲六维评分、硬规则、独立评审模型，以及为什么某个回答被判成 Badcase。

5. **进入 Badcase**
   讲归因类型和优化建议如何支持后续 Prompt、知识补充或产品策略迭代。

6. **进入报告和 GitHub 展示**
   说明本地评测结果可以导出成 Markdown 报告、README 截图和 GitHub Pages 静态展示，便于作品集呈现。

一句话节奏：

> 我先用总览页说明整体评测结果，再用一个具体 Case 展示模型差异，然后通过 Badcase 和报告页说明这些结果如何反向指导 Prompt 和产品策略。

## 高频追问回答模板

### 1. 你为什么做这个项目？

我做这个项目不是为了做一个模型调用 demo，而是因为我发现 AI 产品评测里的低效点主要在流程和口径上：评测集、模型回答、评分、Badcase 复盘经常分散在 Excel、文档和不同网页里。这样不仅效率低，而且很难形成统一标准。所以我想把它做成一个轻量平台，让评测结果可以被复盘、比较、展示和继续迭代。

### 2. 这个项目解决的核心问题是什么？

核心问题是：如何用统一口径比较多个模型的回答质量，并把低分原因转化成后续优化动作。它不只是告诉我哪个模型分数高，还要说明为什么低、问题属于什么类型、下一步可以怎么改 Prompt、补知识或调整产品策略。

### 3. 为什么不用唯一标准答案？

因为开放式问答通常没有唯一正确文本。如果强行按固定答案匹配，容易误伤表达不同但本质正确的回答。所以我把参考答案设计成“期望行为 / 评分参考口径”，更接近产品验收标准。比如工具调用类问题，重点不是话术是否一致，而是模型有没有识别工具边界、有没有避免编造实时信息。

### 4. 评分是谁来做的？怎么保证相对公平？

评分分两层。第一层是硬规则，处理空回答、调用失败、伪工具调用、实时信息编造等确定性错误。第二层是独立评审模型，对照用户问题、期望行为和模型回答做六维评分。

公平性上，我做了几件事：所有模型面对同一批 Case，使用同一套评分口径；先用硬规则处理明显错误，避免语言包装掩盖问题；如果被评模型和评审模型相同，会自动切换备用评审模型，降低自评偏差；每条评分保留原因和优化建议，方便复核。

### 5. 评审模型本身也会有偏差，你怎么看？

我会承认它有偏差。当前版本不是要证明自动评分绝对客观，而是作为一个统一口径的自动初筛系统，提高评测效率和一致性。后续如果进入真实团队使用，我会加入人工复核、多评审模型投票和黄金样本校准，尤其是对安全合规、高风险工具调用这类场景。

### 6. 为什么要做回答存档？

回答存档主要解决三个问题：第一是成本，重复演示或回归时不必每次重新调用 API；第二是稳定性，同一批样本可以复用历史回答，便于比较评分和优化结果；第三是演示效率，新增 Case 可以只生成缺失回答，而不是重跑全部数据。

### 7. 为什么要做 GitHub 静态展示？

因为 FastAPI 后端只能在本地运行，但项目作为作品集需要能长期展示。我的做法是把已完成的评测结果导出为 `demo-data.json`，前端在没有后端时自动读取静态快照，同时 README 也会展示关键页面截图。这样项目既能本地动态评测，也能在 GitHub Pages 上常驻展示。

### 8. Gemini 总览总结的产品价值是什么？

它的价值不是替代具体评分，而是把分散的评分数据、模型表现和 Badcase 类型整理成更适合汇报的产品结论。对于产品经理来说，单条分数还不够，面试或团队汇报时更需要说明整体表现、主要问题和下一步建议。

### 9. 这个项目最难的地方是什么？

最难的不是前后端实现，而是评测方法设计和产品取舍。比如期望行为怎么写，既不能太空，也不能变成机械标准答案；不同场景下“好回答”的定义也不完全一样；同时，MVP 不能无限加功能，所以我优先做了本地可跑、评分可解释、结果可导出、展示可复用这几件事。

### 10. 这个项目和普通多模型展示页有什么区别？

普通多模型展示页主要是把几个回答放在一起看，而这个项目更强调评测闭环和展示闭环。它有评测集、评分维度、Badcase 归因、优化建议、Prompt 迭代、Gemini 总结、报告导出和 GitHub 静态展示。也就是说，它不是只展示结果，而是帮助产品经理完成“发现问题 - 解释问题 - 推动优化 - 对外展示”的工作流。

### 11. 你在项目里体现了哪些产品经理能力？

主要有四类：

1. 问题抽象能力：把零散评测流程抽象成标准化闭环。
2. 评测体系设计能力：定义场景、维度、Badcase 类型和评分口径。
3. 数据和结果复盘能力：不仅看总分，还看原因、类型分布、总结结论和优化方向。
4. 产品落地能力：把方法论做成一个可运行、可展示、可迁移、可迭代的工具。

### 12. 如果继续迭代，你会优先做什么？

我会优先做三件事：

1. 把期望行为从文本升级为结构化评分点，比如关键步骤、扣分项和风险项。
2. 给高风险和高分歧样本增加人工复核。
3. 对工具调用、安全合规等场景引入差异化评分权重。

如果时间更充裕，还会补 Prompt A/B Test、回归测试集管理、多评审模型交叉评分和黄金样本校准。

### 13. 如果面试官问：这是产品项目还是技术项目？

我会说它本质上是产品项目，技术只是承载方式。因为我最想展示的是我对 AI 产品评测的理解：怎么定义评测口径，怎么尽量保证相对公平，怎么让评测结果支持后续产品决策，以及怎么把结果沉淀成可展示的作品集资产。这些比单纯调通模型 API 更能体现产品经理能力。

## 面试中要避免的说法

1. 不要说“这个系统可以完全客观评测模型”。更稳的说法是“提升一致性和可复盘性”。
2. 不要过度强调技术栈。产品经理面试里技术栈是加分项，不是主线。
3. 不要把“自动评分”讲成完全替代人工。更合理的定位是“自动初筛 + 重点样本复核”。
4. 不要直接说“我评测了所有主流模型”，除非你能拿出具体数据和样本。
5. 不要只讲功能列表，要讲每个功能解决了评测流程里的什么问题。
6. 不要把 GitHub 展示说成线上 SaaS。它是静态展示模式，动态评测仍在本地完成。

## 一句话收尾

> 我做这个项目不是为了证明我会调模型 API，而是想展示我对 AI 产品评测这件事的理解：怎么定义口径，怎么保证相对公平，怎么把 Badcase 转化成后续 Prompt 和产品策略迭代，并把评测结果沉淀成可复盘、可展示的产品资产。
